DevDesk / Product UI

UI improvement plan

A prioritized implementation plan for making the DevDesk desktop app clearer, more consistent, more accessible, and faster to use without expanding product scope.

Status: Ready for implementation Scope: Renderer UI Priority: P0 → P2 Source: Four read-only UI audits
Outcomes Priorities Phases Acceptance Validation Risks
01 / Direction

Desired outcomes

Scan faster

Use a smaller, predictable typography and spacing scale so project, command, history, and status information is easy to parse.

Know what happened

Give every asynchronous action a visible loading, success, failure, and retry path.

Stay in context

Keep project-aware actions and state visible while moving between terminals, history, Git, health, notes, and automation.

Guiding principle: improve clarity and confidence before adding new features. Prefer shared primitives and semantic tokens over one-off Tailwind overrides.

03 / Delivery sequence

Implementation phases

Phase 0 — Foundation

Dependencies: none · Target: shared UI layer

  • Add semantic surface, status, code-surface, and typography tokens.
  • Create shared Panel, EmptyState, LoadingState, ErrorState, and StatusNotice components using shadcn/Radix conventions.
  • Add IconButton/ToolbarButton where raw buttons repeat the same interaction pattern.
  • Complete the components/ui/index.ts barrel exports.
  • Correct Badge semantics and document when primitives should be used.

Phase 1 — Shell and context

Dependencies: Phase 0 · Target: orientation and navigation

  • Clarify “Engine,” “Commands,” and terse project-tab labels with names or subtitles.
  • Expose a persistent project-context switcher where project-scoped actions are available.
  • Make the sidebar’s default/collapsed behavior understandable and keyboard-safe.
  • Add visible shortcut/help discovery for Quick Launcher and fullscreen.
  • Standardize project header state: path, branch, health, indexing, and active processes.

Phase 2 — Feedback and safety

Dependencies: Phase 0 · Target: confidence in operations

  • Give async actions consistent loading, success, failure, retry, and saved states.
  • Replace silent Git “Unavailable” fallbacks with actionable state distinctions.
  • Confirm project deletion, history clearing, container stop, and bug deletion with explicit scope.
  • Add undo/export/recovery guidance where technically feasible.
  • Show autosave status and last-saved information for notes.

Phase 3 — Responsive and accessible UI

Dependencies: Phase 0 · Target: constrained windows and keyboard users

  • Stack, drill into, or drawer-enable fixed list/detail layouts below the desktop breakpoint.
  • Remove nested interactive elements from terminal tabs and provide named icon buttons.
  • Add menu/dialog semantics, Escape handling, focus transfer, and focus restoration to terminal overlays/menus.
  • Test dialogs at narrow widths and increased text size; preserve scroll access.
  • Raise critical metadata from 9–10px and verify contrast in both themes.

Phase 4 — Workflow acceleration

Dependencies: Phases 1–3 · Target: high-frequency tasks

  • Add “Run and view output” and “Open in History” actions to command execution.
  • Preselect the active project for project-scoped command, terminal, and Git actions.
  • Expose common Git actions directly in the project Git tab.
  • Add search/filter/sort to History with duration, exit code, and failure summaries.
  • Make terminal tabs show project and working-directory context; warn before closing active work.

Phase 5 — Visual polish and QA

Dependencies: all prior phases · Target: release confidence

  • Reduce card/border noise and normalize page padding and vertical rhythm.
  • Improve empty states with a clear explanation, primary CTA, and helpful next step.
  • Replace hard-coded command/terminal colors with theme tokens.
  • Run renderer tests, typecheck, lint, and packaged manual QA.
  • Capture before/after screenshots for the main shell, Projects, Commands, History, and Terminal screens.
04 / Definition of done

Acceptance criteria

Visual system

  • Feature screens use shared semantic surfaces and feedback components.
  • No new arbitrary typography or status colors are introduced without a documented reason.
  • Spacing and metadata sizing are readable at normal desktop density.

Interaction

  • Every async action visibly communicates loading, success, failure, and retry where applicable.
  • Destructive actions state what will be removed/stopped and require an intentional confirmation.
  • Common project workflows preserve project context and minimize unnecessary navigation.

Accessibility

  • All icon-only controls have accessible names.
  • No nested interactive controls remain.
  • Dialogs, menus, overlays, focus order, Escape behavior, and focus restoration work with keyboard input.

Responsive behavior

  • Projects, Commands, History, and detail views remain usable in a narrow window.
  • Dialogs retain reachable headers, actions, and scroll regions at constrained sizes.
  • Critical content remains readable with increased text size and dark/light theme changes.
05 / Verification

Validation plan

  1. After each phase, run the smallest relevant renderer test suite and perform a manual smoke pass of affected workflows.
  2. Use viewport checks at approximately 1280px, 900px, 700px, and 400px widths. Test keyboard-only navigation and focus visibility.
  3. Test both themes, long project names/paths, empty data, slow loading, failed IPC calls, and active terminal processes.
  4. Run repository gates before merging: npm run typecheck, npm run lint, and relevant renderer tests.
  5. Before release, run npm run release:gate and update the interactive workflows in manual QA.
npm run typecheck
npm run lint
npm run test:renderer:run
npm run release:gate

Automated checks do not replace packaged-app interaction testing. Record manual results separately for Windows and Linux, following the repository’s QA evidence rules.

06 / Guardrails

Risks and non-goals

Risks

  • Large shared-component changes can create broad visual regressions.
  • Changing project context may affect IPC assumptions and persisted selection state.
  • Responsive terminal work needs real packaged testing, not source inspection alone.

Non-goals

  • No new cloud services, analytics, or background daemons.
  • No wholesale navigation rewrite before the existing workflows are made clear.
  • No feature expansion unrelated to usability, accessibility, consistency, or feedback.
Recommended first slice: implement Phase 0 plus the highest-risk items in Phase 2 and Phase 3. This creates reusable UI foundations while addressing destructive actions, terminal semantics, and narrow-window usability.
