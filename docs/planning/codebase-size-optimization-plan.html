DevDesk / Engineering Health

Index scope & codebase modularity plan

The Performance Engine shows DevDesk itself at 361 files / 20 MB (excluding node_modules), while peer projects such as localbase (~251 files / 2.1 MB) and Petlink (~176 files / 1.8 MB) report much smaller source sets. The displayed MB is the sum of indexed file sizes—not the SQLite database footprint. This plan therefore separates index scope from codebase modularity; they require different work and different success metrics.

02 / Full toolkit

Every lever (not only god files)

Run index-scope and maintainability work as separate tracks, with shared measurement and validation.

A Split god files

Break mega-modules by domain so reviews, tests, and mental models stay local. Highest leverage for day-to-day velocity.

B Engine index policy

Give users explicit source-first, source-plus-docs, and full-text scopes; report logical and physical index size separately.

C Repo hygiene

Remove stray screenshots, duplicate assets, and committed bulk that is not product source. Tighten ignore rules.

D Architecture boundaries

Thin App.tsx, domain IPC modules, feature state hooks, lazy section loading—align with docs/architecture/module-boundaries.md.

E Dead weight & duplication

Delete unused code paths, dual type emits, and inlined helpers that already exist as services.

F Guardrails

File-size budgets, complexity lint, architecture checks, and “no new god files” in review—so the win sticks.

Target north stars (12 weeks): (1) no new source file > 600 lines without an explicit, owned exception; (2) source-first indexing excludes known non-source paths and shows a reproducible reduction against the same commit; (3) App.tsx orchestration-only (< ~400 lines); (4) CI fails on new files over budget or new IPC handlers outside domain modules.

04 / Lever B

Engine & index optimization

Peer projects are not just “better written”—they are smaller products with less non-source text under the repo root. DevDesk indexes itself as a monorepo that includes docs, plans, landing, and large TS units. First control what is indexed; evaluate storage changes independently against physical database size, search correctness, and latency.

B1 — Source-first index profiles Product

  • Add an engine ignore layer on top of .gitignore (e.g. .devdeskignore or project settings): default templates for “source only,” “source + docs,” “everything text.”
  • Default profile for app projects should exclude: docs/planning/**, **/*.html (except maybe apps/*/index.html), packages/landing/** when indexing the monorepo as DevDesk, root marketing markdown, screenshots, coverage, release/, dist/.
  • Respect language policy more aggressively: optional skip of pure Markdown/JSON unless the user opts in (today shouldIndex only skips binary/image/font/lockfile).
  • Surface “why is this large?” in Index Summary: top files by size, top paths by folder, skipped count, profile name.

B2 — Storage model Product

  • Measure before redesign: report the SQLite file size and searchable-content bytes separately from logical indexed bytes.
  • Metadata-first spike: test storing content only for searchable text under a measured cap. Preserve FTS ranking, fallback search, incremental identity, and offline behavior before adopting it.
  • On-demand content spike: reading current files at result-expansion time is acceptable only if deleted/moved files, stale indexes, and search-result consistency have defined behavior.
  • Content size cap + warning: already skip binary; add soft skip for “huge text” (minified bundles, generated maps if not gitignored).
  • Gate any storage migration on equivalent search recall, unchanged regex behavior, migration tests, and a measured physical-size or latency benefit.

B3 — Scanner improvements Engine

  • Confirm packaged skip dirs (already skip node_modules, release, etc. in Rust walker) cover packages/engine/rust/target, coverage, and Windows AppData paths when mis-pointed.
  • Optional monorepo mode: index only apps/* + packages/engine + packages/ipc-contracts when project type is “DevDesk monorepo.”
  • Index Summary UX: show “effective sources” vs “supporting files” so 20 MB never surprises users.
Dependency: the scanner currently honors Git ignore rules, not .devdeskignore. Implement and test the engine ignore layer first; only then commit a profile and measure the before/after reindex on the same revision.
05 / Lever C

Repository hygiene

Remove or relocate bulk

  • Root screenshots / ChatGPT images already gitignored—ensure they are not still on disk under the project path the engine scans.
  • Large logo option PNGs under apps/renderer/assets/ (~450 KB each): keep only assets the app ships; move design explorations out of the indexed tree.
  • Keep useful engineering plans versioned in the repository; exclude completed or non-source plans from source-first indexing rather than moving them to an external system solely to lower a metric.

Monorepo boundary for “self” projects

  • packages/landing is a separate deployable. When DevDesk indexes its own code for search, landing screenshots and marketing copy should not count against product intelligence.
  • Prefer an explicit monorepo index profile over splitting deployables into separate repositories solely to lower self-index metrics.

Generated & dual artifacts

  • Avoid committing both types.ts and generated types.js / stale types.d.ts if any remain under renderer.
  • Keep dist/, coverage/, release/ gitignored (already) and engine-skipped (verify).

Markdown sprawl

  • Root has many parallel agent guides (AGENTS.md, CLAUDE.md, GEMINI.md, etc.). Consolidate shared rules into one source and thin wrappers if needed—less duplicated prose in the index.
  • Archive completed milestone plans; keep only living docs.
06 / Lever D

Architecture moves (structure without “just split files”)

D1 — Feature slices over mega-shell

  • Introduce lightweight feature modules under apps/renderer/app/features/{projects,commands,containers,engine,git,bugs,history,terminal}/ each owning section UI + hooks + local types.
  • App.tsx becomes a composition root: providers, tab router, global dialogs host.
  • Lazy-load heavy tabs with React.lazy so cold start and mental load track feature use (optional; measure first).

D2 — Domain IPC packages

  • ~100 ipcMain.handle registrations today, dominated by projects (12), bugs (11), commands (9), engine/containers (8).
  • Pattern: registerXHandlers(deps) + shared IpcContext (window, store, services).
  • Move non-handler helpers (WSL path parsing, Docker spawn, chain execution) into existing service folders so IPC files stay pure wiring.
  • Align channel names with packages/ipc-contracts; generate preload stubs where possible.

D3 — Continue store modularization

  • apps/desktop/data/store/ is already split (good). Apply the same discipline to any remaining fat modules (core.ts, normalize.ts, bugs.ts).
  • Keep schema (model.ts) as types + migrations only—no orchestration.

D4 — Shared UI extraction (reduces line bloat)

  • Many 400–1,000 line sections reimplement filters, empty states, dialogs, and toolbars. Shared Panel/Empty/Error primitives (see UI improvement plan) cut duplicated JSX mass.
  • Prefer composition over copy-paste growth when adding new project tools.

D5 — Codegen for boilerplate

  • IPC channel list → preload method map → renderer ElectronAPI types from one source of truth.
  • Eliminates triple-maintenance bloat and prevents “types file” growth (currently large types.ts / types.d.ts).

08 / Lever F

Guardrails so the bloat does not return

Budgets

  • Existing baseline: retain check-architecture.mjs warnings at 400/600 lines while the P0 files are decomposed.
  • Hard: fail CI for new files over 800 lines or growth in an allowlisted file; each exception records an owner, reason, removal ticket, and review date.
  • Ratchet: reduce the allowlist as domains are extracted; do not force meaningless splits to reach zero by an arbitrary release.

Lint & architecture

  • ESLint max-lines, max-lines-per-function, complexity caps for new code.
  • Extend scripts/check-architecture.mjs to forbid new handlers in registerIpc.ts body beyond re-exports.
  • Renderer: forbid new useState in App.tsx beyond an allowlist (encourage hooks).

Engine self-metrics

  • Show logical indexed bytes, searchable-content bytes, physical SQLite bytes, and largest 10 paths in Index Summary.
  • Optional health badge: “index looks heavy vs language mix.”

Review checklist

  • PR template: “New files > 400 lines? Split plan?”
  • No business logic in IPC registrars or preload beyond validation.
  • Prefer feature folder + test over extending a god section.
09 / Delivery sequence

Phased plan

Order follows dependencies. Capture a reproducible baseline before changing index scope; establish test and dependency seams before moving IPC or renderer state.

Phase 0 — Reproducible baseline & index scope

Risk: low · Effort: 2–4 days · Levers B, C

  • Record commit SHA, exact project root, full/incremental mode, profile, counting script, and pre-change metrics.
  • Add and test engine support for .devdeskignore or persisted project profiles; do not treat the file as active before scanner support lands.
  • Add a source-first profile excluding planning HTML, landing media, root media, and optionally tests; retain source + docs and full-text profiles.
  • Reindex the same commit; capture logical bytes, searchable-content bytes, physical SQLite bytes, files, languages, skipped reasons, and search correctness before/after.
  • Delete or move stray root images still on disk; trim unused large assets under renderer if unused at runtime.
  • Document “how to index this monorepo” in engine section help / data-locations docs.
  • Script: report top 25 largest source files by line count (CI artifact or npm run report:file-sizes).

Phase 1 — IPC & service extraction

Risk: medium–high · Effort: ~1–2 weeks · Lever A, D2

  • Inventory every registered channel and characterize success, validation, authorization, and error behavior with focused tests.
  • Introduce a typed shared dependency context so domain registrars do not capture hidden mutable state.
  • Extract Docker/WSL/command-execution helpers out of registerIpc.ts into services.
  • Split handlers one domain at a time; validate each wave, then leave registerIpcHandlers as a one-page orchestrator.
  • Preserve channel names, sender validation, error semantics, registration order where relevant, and preload contracts.
  • Target: registerIpc.ts < 200 lines; registrars contain wiring and validation, while business logic lives in services.

Phase 2 — App shell & section modularization

Risk: medium–high · Effort: 2–3 weeks · Lever A, D1

  • Wave 2A: characterize bootstrap, terminal, engine, tray, and listener lifecycles; extract bootstrap/subscription hooks without changing ownership.
  • Wave 2B: extract project and feature state from App.tsx; introduce context/providers only where prop drilling hurts.
  • Wave 2C: split Projects, Commands, and Containers one section at a time into co-located feature modules.
  • Wave 2D: reduce CommandPalette into UI shell, pure ranking, and feature-owned providers.
  • Align with UI improvement plan shared primitives to delete duplicated markup.

Phase 3 — Engine product upgrades

Risk: medium · Effort: ~1 week · Lever B

  • Complete profile selection and per-project UI after the Phase 0 scanner/profile foundation.
  • Run a storage-model spike; adopt content caps or on-demand content only when correctness and measured physical-size benefits meet the B2 gate.
  • Index Summary: top files, folder rollup, profile label, skipped reasons.
  • Tests for ignore layer and size caps in packages/engine.

Phase 4 — Guardrails & cleanup wave

Risk: low–medium · Effort: ongoing · Lever E, F

  • CI file-size budgets + architecture rule: no new logic in mega entrypoints.
  • Second-pass splits for git/service, bundler, bug/git panels still over 400 lines.
  • Consolidate duplicated agent guidance only where tool-specific entrypoints and local repository context remain intact; archive completed plans without removing useful history.
  • Optional preload/types codegen from ipc-contracts.
  • Re-run engine self-index; publish metrics in release notes (“maintainability”).
10 / Definition of done

Acceptance criteria

Index health (self-project)

  • Before/after results use the same commit, project root, scanner version, and full-reindex mode.
  • Index Summary reports logical indexed bytes, searchable-content bytes, and physical SQLite bytes as separate metrics.
  • Planning HTML + landing media are not counted by default.
  • Source-first search preserves expected results for a checked-in representative query set; full-text remains available for docs-heavy projects.
  • UI exposes largest paths, folder rollups, profile, and skipped reasons so regressions are obvious.

Structural health

  • No new source file > 800 lines; legacy exceptions cannot grow and carry an owner, reason, ticket, and review date.
  • App.tsx is orchestration-only (< ~400 lines target).
  • IPC registration is domain-modular; registrars contain wiring/validation and helpers live in services.

Process

  • CI enforces size/architecture budgets.
  • npm run release:gate still green after splits.
  • IPC channel inventory, renderer lifecycle tests, engine ignore/profile tests, and representative search-recall checks pass.
  • Manual packaged smoke covers projects, commands, Docker/WSL, git, terminal lifecycle, and engine reindex/search; it remains distinct from automated evidence.
  • Docs updated: module boundaries + this plan linked from ROADMAP/TODO if tracked.

Non-goals

  • Not a feature freeze excuse—features still land in feature folders.
  • Not deleting tests to lower file count.
  • Not optimizing node_modules (already excluded).
  • Not merging many small files into fewer large ones for vanity metrics.
11 / Risks & mitigations

Risks

Regression during IPC split

Many handlers touch shared helpers. Mitigate with existing IPC contract tests + engine-ipc suite + manual smoke of projects/commands/docker/git.

App state extraction breaks listeners

Terminal/engine subscriptions are lifecycle-sensitive. Extract hooks with identical effect deps; keep a single “data load” bootstrap path.

Ignore profiles hide useful docs

Default source-first is right for product code search; keep a “full text” profile for users who want plans/wiki in-index.

Chasing the wrong metric

File count and logical bytes alone are bad KPIs. Track domain ownership, largest modules, changed-file locality, search recall, reindex time, logical searchable bytes, and physical database size.

Success story framing: Petlink/localbase are smaller products. DevDesk will always have more features—and thus more files—than a focused app. “Optimized” means proportionate modules, honest indexes, and no 3k-line catch-all files, not matching a 176-file index by gutting capabilities.
