Phase 3: Embedded Terminals

A practical implementation plan for integrating persistent PTY sessions into DevDesk using node-pty in the main process and XTerm.js in the renderer, with full WSL support and project-scoped terminal tabs.

4 features Manager, UI, tabs, palette shortcuts
9-11 hrs Estimated total roadmap effort
v1.3 Release milestone with in-app terminals
High Primary roadmap priority

Objective

Keep developers inside DevDesk by providing embedded terminal sessions that feel native. The implementation must support Windows (conpty), macOS, Linux, and WSL paths; reuse existing shell-resolution logic from preferences; and stream PTY output to the renderer without blocking the UI.

Source: Phase 3 in ROADMAP.md. This plan keeps the roadmap scope intact and expands it into implementation order, contracts, UI behavior, and acceptance criteria.

Core Data Contract

Planned Shared terminal types for the main and renderer layers.

Keep the session shape small and renderer-friendly. The main process owns the PTY lifecycle; the renderer consumes already-normalized output chunks. 

interface TerminalSession {
  id: string
  projectId?: string
  cwd: string
  shell: string
  createdAt: string
  cols: number
  rows: number
}

interface TerminalCreateOptions {
  projectId?: string
  cwd?: string
  shell?: string
  cols?: number
  rows?: number
}

IPC Surface

Channel Direction Payload Description
terminal:create invoke → main TerminalCreateOptions Spawns a PTY and returns { terminalId: string }.
terminal:write invoke → main { terminalId: string; data: string } Writes keystrokes / input to the PTY stdin.
terminal:resize invoke → main { terminalId: string; cols: number; rows: number } Resizes the PTY to match the renderer container.
terminal:close invoke → main { terminalId: string } Kills the PTY process and removes the session.
terminal:data main → renderer { terminalId: string; data: string } Streams PTY stdout/stderr output to the renderer.
terminal:exit main → renderer { terminalId: string; code?: number } Notifies when the PTY process exits.
terminal:error main → renderer { terminalId: string; error: string } Surfaces spawn or runtime errors from the PTY.

UI Behavior

Terminal Creation Flow

  • User clicks "+" in the project terminal tab bar or selects a palette action.
  • Renderer invokes terminal:create with projectId and optional cwd.
  • Main process resolves the project path, determines the shell from preferences.terminal, and spawns node-pty.
  • Session ID is returned and the renderer mounts a Terminal component for that ID.

Data Flow

  • Main PTY emits data events as the process writes to stdout/stderr.
  • TerminalManager broadcasts terminal:data via BrowserWindow.webContents.send.
  • Renderer receives the event and writes the chunk into the active XTerm.js instance.

Input Flow

  • XTerm.js captures key events via its onData handler.
  • The Terminal component invokes window.electronAPI.terminalWrite(id, data).
  • Preload forwards terminal:write to the main process IPC handler.
  • TerminalManager writes the data to the PTY stdin for that session.

Resize Flow

  • A ResizeObserver on the terminal container detects dimension changes.
  • FitAddon calculates the new column/row count from the container size.
  • Renderer invokes terminal:resize with the new dimensions.
  • Main process calls pty.resize(cols, rows) so the shell receives a SIGWINCH equivalent.

Cleanup Flow

  • Closing a tab invokes terminal:close and unmounts the XTerm.js instance.
  • Main process kills the PTY process and deletes the session from the internal Map.
  • On app quit, all remaining PTY processes are terminated before the main process exits.

WSL Support

WSL projects must open an interactive bash session inside the correct distro instead of the Windows default shell. Reuse the existing parseWslProjectPath and WSL_EXECUTABLE_PATH patterns already defined in apps/desktop/ipc/registerIpc.ts.

When a project path matches \\\\wsl.localhost\\<distro>, the terminal manager should spawn the PTY with:
wsl.exe -d <distro> -e bash -l

This ensures the terminal starts in the user's WSL home and respects .bashrc / .profile. The working directory can then be changed to the project linux path via an initial cd command or by passing --cd if the WSL version supports it.

Acceptance Criteria

  1. Planned terminal:create spawns a PTY and returns a stable terminalId for Windows, macOS, and Linux.
  2. Planned terminal:data streams PTY output to the renderer in real time without UI jank.
  3. Planned XTerm.js renders output and captures keyboard input for the active terminal; copy/paste works.
  4. Planned terminal:resize updates PTY dimensions when the container resizes, and FitAddon keeps the terminal sized correctly.
  5. Planned Terminal tabs allow multiple sessions per project with independent lifecycle and tab labels.
  6. Planned Closing a tab kills the PTY process and removes the renderer instance without leaking resources.
  7. Planned Command palette shows "Open terminal in [Project Name]" and "Close all terminals" actions.
  8. Planned WSL projects use wsl.exe -d <distro> -e bash -l as the shell backend via existing path helpers.

Risks

Native Module Rebuild

node-pty must be rebuilt against Electron 33 ABI headers. Add an electron-rebuild step or use @electron/rebuild in the build pipeline so CI and fresh clones compile correctly.

Windows Conpty Compatibility

Windows PTY behavior depends on the conpty backend and varies by OS version. Test on Windows 10 and 11. If conpty causes issues, node-pty can fallback to winpty, but prefer conpty for Unicode and color support.

Security

Never execute arbitrary shell strings from the renderer. Only spawn the shell resolved from preferences.terminal (or the WSL fallback). Do not expose a generic "run any command" IPC for the terminal layer.
