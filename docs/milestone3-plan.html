Milestone 3 — Backup, Restore & Tray Quick Actions

Allow users to back up and restore all DevDesk data, and provide system tray quick actions for common workflows.

3 Tasks Electron + Vite + TS SQLite / better-sqlite3 React + shadcn/ui

Milestone Goal

Ship a robust export/import system that serializes the entire SQLite database to a versioned JSON backup, validates and restores it safely with replace or merge modes, and backs up the current database first. Additionally, add a native system tray icon with quick actions — Show DevDesk, New Terminal, Run Last Command, and Quit — with platform-aware icons and a user preference to enable or disable the tray.

Export/Import — Backend

Backend Done

Serialize all DB tables to a single JSON file and safely restore from it. Validate schema versions, back up the current database before restoring, and support both replace and merge modes.

Implementation Details

  • exportAllData(): Read all tables (projects, commands, chains, triggers, run_history, notes, preferences, engine_indexes, search_sessions, health_check_runs, health_check_items, bug_reports, bug_attachments, context_snapshots) into a single JSON object.
  • Export format header: { version: number, exportedAt: string, platform: string }
  • importAllData(): Validate schema version. Reject imports from newer app versions. Backup current devdesk.db to devdesk.db.backup-<iso> before restoring.
  • Support replace mode (wipe then insert) and merge mode (upsert existing records).
  • External attachments: For v1, exclude external attachment files and warn the user; include only DB-resident data.

Acceptance Criteria

  • Export writes all tables to a single JSON file with the correct header.
  • Import validates schema version and rejects backups from newer app versions.
  • Current devdesk.db is backed up to a timestamped file before any restore operation.
  • Replace mode wipes existing data and inserts imported records cleanly.
  • Merge mode upserts records without losing unrelated existing data.

Risk Summary
High Data Loss During Import

A failed or interrupted import in replace mode could leave the database in an inconsistent state if transactions are not handled correctly.

Mitigation: Always run imports inside a SQLite transaction. Perform the timestamped DB backup before starting. Roll back on validation or write failures.
Medium Version Mismatch in Backups

Future schema changes may make older or newer backups incompatible. Restoring a newer backup into an older app could corrupt tables.

Mitigation: Strictly validate the version header. Reject imports from newer versions. Maintain a version compatibility map and document migration rules.
Medium External Attachment Path Issues

Bug report attachments stored outside the DB will not be included in v1 exports, leading to broken references after restore.

Mitigation: Warn the user clearly during export and import. Document the limitation. Consider embedding small attachments in the DB for a future v2 format.
Low Tray Icon Platform Differences

macOS requires template images, Windows needs DPI-aware icons, and Linux tray behavior varies across distributions.

Mitigation: Use platform detection (process.platform) to set templateImage on macOS and provide multi-resolution PNGs for Windows. Test on each target OS.
Low IPC Channel Conflicts

Adding config:export, config:import, and tray-related channels may collide with existing or future channel names.

Mitigation: Follow the existing kebab-case namespace pattern (config:, tray:). Audit registerIpc.ts before merging to avoid duplicates.
Medium Large Export File Size

As the database grows (run history, health checks, bug reports), the JSON export could become very large and slow to write or parse.

Mitigation: Stream writes where possible, or use JSON.stringify with a buffered approach. Warn users if the export exceeds a threshold. Offer table filtering in a future release.
